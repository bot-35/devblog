    ## A propos du framework
    Astro est un framework JavaScript prévu pour développer des sites web **multi-pages** (Multi Page App - MPA). 
    
    La promesse de ses fondateurs et de nous aider à construire **rapidement** un site orienté sur le **contenu**.

    ## MPA & SPA 

    Il existe deux types d'architectures pour développer une application web :

     - **MPA** (Multi Page App)
     - **SPA** (Single Pape App)


    ### L'architecture MPA (Multi Page App)

    Dans une architecture MPA, chaque **action** de l’utilisateur déclenche une **requête HTTP** vers le serveur qui fournira à **chaque fois** en réponse une page web.

    Le développeur devra donc écrire **toutes** les pages nécessaires au bon fonctionnement de son application. 


    <ImageBox  src={MPA} alt="Diagramme représentant le fonctionnement de l'architecture type MPA."  orientation="horizontal"/>

    #### Avantage

    - **Simple** à comprendre.


    #### Inconvénients 
    
    - **Beaucoup** de répétition dans le processus de développement.
    - Chaque page devant être codé **séparément**, on finissait souvent par avoir des sources pleines de dossiers, sous-dossiers et fichiers .html plus ou moins bien classés... 
    - **Les mises à jour** (exemple : changement dans le design) nécessitaient de modifier **tous** les fichiers correspondants.
    

    ### L'architecture SPA (Single Page App)

    En réponse au MPA et à ses lourdeurs, les acteurs du web travaillèrent sur l'**AJAX** et les serveurs JavaScript pour développer le modèle SPA.
    
    Dans cette architecture, le serveur fournis une **unique** page web (<Icon pack="ph" name="file-html-light" class='h-8 inline' /> + <Icon pack="ph" name="file-css-light" class='h-8 inline' />+ <Icon pack="ph" name="file-js-light" class='h-8 inline' />) en réponse à la première requête de l'utilisateur puis c'est le JavaScript qui se chargera de répondre aux actions des utilisateurs en modifiant le DOM.

    <ImageBox  src={SPA} alt="Diagramme représentant le fonctionnement de l'architecture type SPA."  orientation="horizontal"/>

    Pour faciliter la mise en place de ce type d'architecture, les géants du web  (Facebook, Microsoft...) ont développés et partagés leurs **frameworks** JavaScript. 

    Leurs succès fut si fort qu'aujourd'hui le modèle SPA est devenu quasiment **indissociable** de ces derniers bien qu'il soit encore tout à fait possible d'en faire sans eux. 

    Chaque solution ayant sa propre logique, retenons surtout qu'il vous faudra **"build"** (construire) votre code.

    **Build** ? Kezako ?...

    Pour faire simple le développeur écrit du code compréhensible par le framework, et c'est ce dernier qui durant l'opération de build ce chargera d'écrire un fichier JavaScript utilisable par tous les navigateurs.

    #### Avantages
    
    Cette architecture à plusieurs atouts :

    - Une seule page, c'est plus **simple** et plus **fluide** pour l'utilisateur, cela ressemble davantage à une application desktop ou mobile.
    - Pour les développeurs, cela ouvre la voie aux **composants** réutilisables et adaptables à souhaits.
    - Une fois la page enregistrée dans l'ordinateur de l'utilisateur, on peut continuer à utiliser le logiciel en **mode hors connexion ou dégradé**.


    #### Inconvénients

    - Le JavaScript doit impérativement être activé chez l'utilisateur.
    - La **conception** de l'application devient une obligation. 
    <br/>Les éléments étant **liés**, il faut bien avoir en tête ce **vers quoi l'on tend**, au risque de se retrouver à modifier de nombreuses fois le même composants au grès des ajouts et modifications sur d'autres. 
    - Dans le cadre d'un 'petit' projet, le fait de devoir se **former** à un framework et à sa philosophie peut paraître **excessif** 🥴. 
    - Enfin, sachez que votre **référencement** par les moteurs de recherche posera **problème**, ces derniers étants basés sur les **liens** entre les différentes pages qui sont ici absents. 

    ## Astro, le meilleur des deux mondes

    On a donc le choix entre un modèle simple (MPA), mais **fastidieux** à mettre en place et à côté un modèle plus **complexe** à appréhender (SPA) mais qui **facilite** grandement le travail du développeur une fois maîtrisé.

    Et c'est ici, juste ces deux modèles qu'Astro vient s'installer. 

    ### Concepts de base

    Astro est un SSG (static site générator), pensé en priorité pour **construire des pages HTML** et qui contrairement aux framework SPA ne nécessite  **aucune librairie JavaScript client** préalable.

    Par contre, comme un framework SPA, il rendra la création de vos sites web **plus simple et plus rapide** en vous apportant notamment la magie des **composants** et autres **'layouts'** (dispositions).
    
    Son fonctionnement est assez simple : 
    
    - Vous codez des fichiers **.astro** que nous détaillerons plus tard, mais qui pour résumer sont un mélange d'HTML CSS et JS.
    - Vous lancez un **build** et le framework ce chargera alors d'écrire tout le HTML, le CSS et le JS, vous fournissant au final un **site web MPA**.
    - Et si besoin, vous **modifiez** vos fichiers .astro. Le framework ce chargera alors de faire la **mise à jour des pages impactés**.

    ### index.astro 

    Un fichier .astro ce découpe en **deux** parties principales :

    - La partie dédié au **serveur**, écrite en **JavaScript**, qui se chargera de traiter les **opérations** tel que : Création des pages, traitement des données etc... .
    - La partie dédié au **rendu**. Cette partie étant elle-même découpée en **trois** parties distinctes : 
        - L'**HTML** <Icon pack="ph" name="file-html-light" class='h-8 inline' />
        - Le **CSS** <Icon pack="ph" name="file-css-light" class='h-8 inline' />
        - Le **JavaScript** qui sera exécuté **côté client** <Icon pack="ph" name="file-js-light" class='h-8 inline' />

    Voici l'exemple d'un **Hello World** sur Astro.


            <CodeBox code={`---
/* ZONE SERVEUR */
/* Ici c'est le JS qui sera traité uniquement
par le serveur pour construire la page */
    const message = "Hello World";
    const title = "My world !";
    const description = "Bienvenue chez moi";

---

<!-- ZONE CLIENT/RENDU -->

<!-- Ici c'est la partie HTML -->
<html>
    <head>
        <meta charset="utf-8" />
        <title>{title}</title>
        <meta name="description" content={description} />
    </head>
    <body>
        <h1 class='message'>{message}</h1>
    </body>
</html>

<script>
/* Ici c'est le JS qui sera exécuté par le navigateur de l'utilisateur */
    console.log('Bonjour à toi ami utilisateur !')
</script>

<style>
/* Ici c'est le CSS de la page */
.message {
    background-color: pink;
    color: rebeccapurple;}
</style>

            `} lang="astro" theme="vitesse-dark" header="index.astro"/>
        

On remarque tout d'abord que la **zone JS du serveur** est encadrée par **deux lignes de tirets**. 

Ce n'est pas seulement esthétique, mais bien une **obligation syntaxique** et ce même si elle reste **vide**.
De plus, cette zone doit **impérativement** se situer au début de votre fichier. 

Tout ce qui ce trouve en dessous de la seconde ligne de tiret concerne le **rendu utilisateur**. 
Ici l'ordre n'a **aucune** importance et dépendra uniquement de votre **goût**.

Voilà nous avons vu **l'essentiel** d'un fichier astro et je suis sûr que comme moi vous êtes **époustouflés** par son élégante  **simplicité** 🍸.

    Mais qu'est-ce qu'un îlot me direz-vous ?
    
    Et bien pour résumer, c'est une solution qui vous permettra de **mélanger** composants static et composants SPA.

    Ces derniers sont **complètement isolés** ce qui implique deux choses : 
    - Les îlots **ne peuvent** entrer en **conflit** avec le reste de l'application.
    - On peut mixer **différents frameworks** dans différents îlots sur une seule et même page !
